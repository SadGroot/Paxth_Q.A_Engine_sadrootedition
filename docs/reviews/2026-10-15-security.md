# Application security review — 15 October 2026

Reviewed with the upstream Agency Agents Application Security Engineer persona, using trust-boundary tracing and checking findings against current callers and tests. This is a source review with small local mocked checks, not penetration testing or a production security certification. No product code was changed.

**Release judgment:** keep unrestricted public deployment blocked until predictable administrator provisioning, the vulnerable spreadsheet reader, and global login exhaustion are addressed. Preserve the existing modular monolith and its working security boundaries.

## Threat model and scope

The installation is explicitly one shared workspace: authenticated users share catalog records, jobs, results, rules and history. Shared reads are not an IDOR under this documented model. Administrators additionally manage users, configuration and destructive operations. A deployment serving mutually untrusted organizations would require a different authorization model before onboarding them.

Boundaries reviewed: public HTTP → JSON parsing/origin/session checks; signed-in user → shared PostgreSQL data and paid jobs; external product pages/workbooks/images → parsers/model/UI; server → model and Crawl4AI credentials. Read authentication/bootstrap, route registration, catalog/configuration/job/image callers, spreadsheet ingestion, model contracts, and the related tests. Older browser-scraping documents were checked against the current fixed Crawl4AI endpoint, rather than assumed current.

## Confirmed findings

### S1 — High: bootstrap silently creates a predictable administrator

**Evidence:** [scripts/bootstrap-admin.ts:10–17](../../scripts/bootstrap-admin.ts#L10) supplies hardcoded username/password defaults, so the subsequent validation passes when overrides are absent. Lines 28–35 insert the account; [.env.example:20–23](../../.env.example#L20) advertises the fallback. The actual password is deliberately omitted here.

**Preconditions/impact:** an operator bootstraps a fresh database without explicit temporary credentials, then exposes login. An attacker who knows the public repository can sign in as administrator and change users/configuration or delete shared data. This does not establish that any existing deployed account uses those credentials; existing usable administrators are protected against accidental bootstrap replacement.

**Smallest fix:** require explicit nonblank `BOOTSTRAP_ADMIN_USERNAME` and `BOOTSTRAP_ADMIN_PASSWORD`, delete both fallbacks and their example comment, and rotate accounts that were provisioned with them. Keep the existing hash validation, transaction and last-admin recovery guards.

**Validation:** a subprocess test with missing/blank overrides must fail before opening a database connection; a disposable-database test must create an explicit account and still reject an existing usable administrator. Test recovery separately.

### S2 — High: an affected spreadsheet parser reads arbitrary vendor workbooks

**Evidence:** [package-lock.json:6984–6985](../../package-lock.json#L6984) locks `xlsx@0.18.5`. [DashboardModule.tsx:351–374](../../src/components/DashboardModule.tsx#L351) reads a chosen file and calls `XLSX.read` and `sheet_to_json` synchronously before any size/row gate; line 457 reads the whole file. Fresh `npm audit` reports GHSA-4r6h-8v6p-xvw6 and GHSA-5pgg-2g8v-p4x9. The maintainer confirms affected arbitrary-file parsing and fixes in [0.19.3 for prototype pollution](https://cdn.sheetjs.com/advisories/CVE-2023-30533) and [0.20.2 for ReDoS](https://cdn.sheetjs.com/advisories/CVE-2024-22363).

**Preconditions/impact:** an editor imports a crafted workbook supplied by a vendor or attacker. The affected parser runs inside the signed-in browser. UI blocking is a realistic impact; prototype pollution impact depends on a usable application gadget and was not demonstrated here. This is not evidence of server code execution. Server-side 10,000-row limits run after browser parsing and do not protect this boundary.

**Smallest fix:** move to a verified fixed SheetJS distribution, pin its exact artifact/integrity, and preserve `.xls`, `.xlsx`, CSV and formatting behavior. Alternatively reuse installed ExcelJS only if the project deliberately drops/replaces its unsupported legacy formats; do not silently remove existing import capability. Add a pre-read byte limit and an explicit post-parse row/cell bound. A file-size gate alone does not fix parser advisories.

**Validation:** supported-format fixtures, leading-zero SKUs, CSV quoting, formatted cells, missing/duplicate headers, maximum sizes and a bounded malicious-input regression. Re-run the audit after locking the replacement. No exploit workbook was executed during this review.

### S3 — High for an exposed login: one client can exhaust authentication for everyone

**Evidence:** [src/server/auth.ts:151–166](../../src/server/auth.ts#L151) keeps a process-wide 100-attempt/15-minute cap, increments it before password verification, and keys per-account attempts by socket address plus username. Line 183 deletes the successful per-account entry but does not reduce the global count. There is no gateway policy supplied with the repository that establishes an independent protective boundary.

**Preconditions/impact:** anyone who can reach login can submit requests with the configured Origin header; that header protects against browser CSRF, not a non-browser attacker. Cycling usernames bypasses the 10-per-key cap while consuming the global budget. Legitimate successful logins also consume it. Existing sessions keep working, but every new login is denied until the window resets. Behind a proxy the socket key normally identifies the proxy, increasing collateral impact. Severity is lower for a separately gated, trusted internal installation.

**Smallest fix:** stop treating a cumulative process-wide counter as a lockout policy. Keep the two-active-scrypt memory guard, enforce scoped failed-attempt throttling at the trusted ingress or shared storage, and ensure successful logins cannot exhaust everybody else's budget. Configure exact trusted proxy boundaries before using forwarded IPs; never blindly trust `X-Forwarded-For`.

**Validation performed:** an isolated Express app with a mocked database and mocked crypto performed 100 successful logins; login 101 returned 429. No real credentials/database were used. Add regressions for repeated failures across usernames, recovery windows, successful traffic, proxy address handling and multiple replicas. `Retry-After: 60` also understates the possible 15-minute lockout and should match the actual remaining window.

### S4 — Medium: unauthenticated requests reach a 50 MB JSON parser first

**Evidence:** [server.ts:29–34](../../server.ts#L29) installs `express.json({limit:'50mb'})` globally before `registerAuth`. Origin checking begins at [auth.ts:134](../../src/server/auth.ts#L134), and session checks at line 188. Thus even a request that will be refused as cross-origin/unsigned is parsed first. [compose.yaml:15–16](../../compose.yaml#L15) caps the app at one CPU and 1.5 GiB RAM.

**Preconditions/impact:** an attacker reaches the HTTP listener and sends multiple accepted-size JSON documents. Buffering and parsing consume memory/CPU before authentication, potentially starving legitimate API/worker work. No crash/load threshold was measured; this is a confirmed missing early resource boundary, not a measured outage.

**Smallest fix:** perform header/origin/session gates before large-body parsing. Give login and ordinary small mutations small limits; reserve the existing large allowance for the authenticated import route with a documented measured budget. Add ingress body/concurrency limits as a second boundary.

**Validation performed:** an isolated app using the same middleware order returned parser 400 for malformed unauthenticated catalog JSON, confirming parsing precedes origin/session rejection. Add an integration test with the real registration order proving oversized/unauthenticated requests are rejected before the import parser or database operation. Check a legitimate maximum import remains supported.

### S5 — Medium: image fetches have a per-response cap but no aggregate admission bound

**Evidence:** [src/server/jobImages.ts:10–51](../../src/server/jobImages.ts#L10) buffers up to 20 MiB per image in chunks, then concatenates the body. Each authenticated GET at lines 86–96 can start independently; there is no shared concurrency/queue limit. [CatalogImagePicker.tsx:14–22](../../src/components/CatalogImagePicker.tsx#L14) starts preparation for each mounted image, and lines 70–75 mount the whole gallery. Model and scrape requests already implement bounded shared admission in their own modules.

**Preconditions/impact:** a signed-in user repeatedly requests a large valid image from an existing completed Catalog run, or users open large galleries simultaneously. Many concurrent requests can aggregate substantially more memory than one response's 20 MiB cap; concatenation temporarily duplicates buffered bytes. A sufficiently large concurrent workload could exhaust the 1.5 GiB container budget and disrupt all users. Browser connection limits may reduce a single UI's concurrency, but do not cap direct authenticated clients. OOM was not induced.

**Smallest fix:** apply a small process-wide image admission limit and bounded queue before opening upstream sockets, releasing on success, error and cancellation. Keep all existing URL/DNS/redirect/type/size checks. Queue or load previews on demand in the picker so opening one dialog does not initiate every preparation immediately.

**Validation:** mocked concurrent fetches must demonstrate a hard maximum on active upstream requests, bounded overflow, queued cancellation, and slot release on failure/oversize/disconnect. A modest controlled load test should establish memory headroom without real provider calls.

## Boundaries that are already sound

- Sessions use random 256-bit tokens with only SHA-256 token hashes stored, finite database expiry and HttpOnly/Strict cookies; production requires Secure cookies and a validated HTTPS `APP_ORIGIN`. Account changes revoke that account's sessions. Passwords use asynchronous scrypt with a bounded number of expensive hashes and constant-time comparison ([auth.ts:5–45,119–149,188–239](../../src/server/auth.ts#L5)).
- The API is registered after centralized authentication/role checks. Users/admins are distinct; last-admin deletion/demotion is guarded and account mutations recheck the actor under an advisory lock. SQL inputs use placeholders or Drizzle parameters. Catalog update columns are chosen from a server allowlist.
- Catalog imports cannot supply server QA results or completion state; current mapping/export functions strip legacy raw QA results. Durable job snapshots, revisions, ownership and dispatch budgets are materially better than accepting browser-owned execution results. Do not reopen this trust boundary while refactoring.
- Image fetches validate public HTTP(S) addresses, reject private/mixed DNS results, pin the checked address, revalidate every redirect, reject SVG/HTML, and cap response bytes and deadlines. Relevant mocked tests cover those cases. No local SSRF bypass was found.
- Product collection sends to a fixed HTTPS Crawl4AI API with redirects disabled for that API request. Model credentials and crawler credentials remain separate and server-only. Provider errors redact keys; model responses are bounded and parsed against application contracts, without shell execution or tool authority. Scraper Markdown suppresses image rendering in its general preview, and the image picker uses the authenticated proxy.

## Hardening and unresolved checks — not confirmed exploits

1. **Remote crawl navigation:** initial DNS validation does not control a third-party crawler's later redirects or fresh DNS lookups. Current code accurately records `finalUrl`/capture time as unknown ([cloudScrape.ts:81–106](../../src/lib/cloudScrape.ts#L81)). Obtain the service's private-address/redirect/egress guarantees and test them against controlled fixtures; do not claim the application's network is reached by this remote navigation without evidence.
2. **Model integrity:** schema validation and instruction separation limit malformed results; they cannot prove factual correctness or immunity to prompt injection. Keep a human review/export boundary and add adversarial evidence fixtures. No arbitrary tool execution, automatic deployment or access to server secrets is exposed to the model here.
3. **Shared paid account:** signed-in users can submit paid runs, previews and scraping; retry/concurrency caps bound individual work but not aggregate user/day spending. Set provider-side spend caps and an operational alert first. Add application quotas only if users' trust model requires them.
4. **HTTP/database/deployment controls:** production header policy (CSP, frame restrictions, HSTS, referrer policy), actual HTTPS gateway behavior, database TLS verification and runtime database privileges are not established by the supplied Compose file. Verify them at the intended ingress/DB rather than infer a current live misconfiguration. Startup runs DDL, so a runtime account with no migration separation currently needs elevated schema privileges.
5. **Notification privacy:** the UI review owns a low-severity issue: notifications survive same-SPA account changes and can show the previous administrator's user-management messages. The menu is hidden while signed out and ordinary catalog/job content is already shared, so this is account-boundary hygiene rather than an authentication bypass. See the [UI review](2026-10-15-ui-accessibility.md).

## Verification limits

Read `.env.example` but not `.env` or live secrets. No production database, paid provider, live crawl, malicious workbook, container stress test, or external attack was used. Existing security/auth/image tests were inspected; full lint/test/build/audit results and disposable-database availability are reported separately in the combined review. The temporary login/parser reproduction used mocked crypto/database in an isolated child process. Historical reports are supporting context, not proof of present deployment state or complete secret-history absence.
